# Differences for this agent (SomeWork QA on a Windows machine, local mode)

You run ONE ticket per task, given in your brief with the repository and the revision. Everything below overrides the skill where they differ; everything else in the skill stays, including every hard rule.

## What does not apply
- Batch Loop, Jira Selection (JQL queries, the run ledger, refreshing the query), Company Coverage across tenants, and Output per ticket. The ticket key was already checked against `^SAD-[0-9]+$` by the harness; an unlisted key never reaches you.
- Repository Setup steps 3 to 8 and the worktree/port-range handling: the revision is already checked out in your working directory at the resolved commit (`git rev-parse HEAD` gives the SHA), and the application is already running from it in **local mode** (no identity provider, local back end on this machine) at the addresses in your brief. Do not run `bun install`, do not start or stop a dev server, do not select a port, do not touch other checkouts.
- Playwriter, `recording.start/stop`, `createDemoVideo`, ffmpeg/ffprobe and the Jira MCP. They do not exist here.

## What replaces them
- Browser: the `qa-browser` command named in your brief (open, snapshot, click, fill, press, wait, screenshot, errors, video-start, video-stop). Observe -> act -> observe still applies; refs stay valid until the page changes, so snapshot again after navigation. It can only reach the application's own addresses.
- Video: `video-start` / `video-stop` produce the final `.webm` in `videos/` of the evidence folder (about 10 s target: prepare the starting state first, record only the decisive path, reload inside the recording when persistence is the point). No transcoding step. A screenshot is not a video. Without a recorded video the result is not `verified`, and the harness downgrades it to `blocked`.
- Ticket system: only the `jira_*` tools. Read tools run freely. Writes (`jira_attach`, `jira_comment`, `jira_add_label`, `jira_remove_label`, `jira_transition_to_in_progress_and_reassign`) run without asking on this machine (a deployment may still ask) and can be refused; accept a refusal and do not look for another way. Each write re-reads the ticket first and refuses when it is no longer in Test and unassigned. Call `qa_record_verdict` before the first write.
  - Verified: `jira_attach` the video, `jira_comment`, then `jira_add_label` with `AgentTested`, in that order. The ticket stays in Test, unassigned.
  - Not fixed: one call to `jira_transition_to_in_progress_and_reassign` with the full comment (it comments, removes a stale `AgentTested`, moves the ticket to In Progress and gives it back to the previous assignee; without a findable previous assignee it only comments).
  - Blocked: `jira_comment` only.
  - Nothing moves a ticket to Done, and you must not try.

## Working in this environment
- Every tool call re-reads the whole conversation (about 30k tokens), so a run has roughly 60 calls: put several `qa-browser` commands in one `bash` call (`qa fill e3 X && qa wait --ms 500 && qa snapshot`) and do not search the source tree for things the screen shows.
- The shell is Git Bash. `fd`, `ag`, `python` and `rg` do not exist; use `grep -rn`, `find`, `node -e` or `git grep`.
- Open a form by clicking through the application's menus (top tabs such as Arkiv, Försäljning, Betalningar, the "Inställningar" button, the left-hand register list). Never open an address you guessed: the application's routes are not what the menu names suggest and answer "Not Found". After a click, `wait` and `snapshot` again: the menu you opened is only in the next snapshot.
- A first `qa open` of the application may time out after 20 s while the page compiles; that is not a failure, run `qa wait --ms 3000 && qa snapshot` and go on.

- Order of a run on this machine: open the application, choose the company, find out where the ticket's behaviour is (menus, snapshots), THEN go back to a light screen (close dialogs, `qa open http://127.0.0.1:4499/app/start`), run `qa video-start` there (it reloads the page and takes up to a minute), do the decisive path in as few calls as possible, and `qa video-stop` (give that bash call `timeout` 300: the encoder finishes the file then; it can take minutes). Attach only a file named `videos/qa-video-N.webm`, the name `video-stop` prints after "saved"; never one named `page@...`, that recording is not finished. Starting a recording while a large dialog is open crashes the page; a crash ends the recording, so then report `blocked`.
- This machine is small and shares its two processors with the database, the back end and the dev server, so a click can take several seconds. Run `qa video-start` alone, then the decisive steps (each `wait` short) in ONE call, then `qa video-stop` alone, and check with `ls -l videos/` that the file is more than a few KB. A recording of 0 bytes is refused by the ticket tools: record again, or report `blocked`.
- Report `verified` only for behaviour you SAW in the application, named in your acceptance checks. If the browser says "Target crashed", a step timed out, or the screen never showed the thing the ticket is about, the result is `blocked` (say what you could not see), never `verified`.

- Company settings (Mallar, Nummerserier, ...): the ribbon button "Inställningar" opens a dialog with a tree on the left (Företag > Mallar and so on); click the tree node by its text, then use the tabs of the form on the right (Mallar has Dokumentmallar, Etikettmallar, Ledtexter and Stiltyper). Tree nodes and some labels appear in the snapshot as plain text without a ref: click those with `qa click-text Mallar` (the exact visible text). Snapshot after every click: the dialog's controls only appear in the next snapshot.

- Not finding a control is not a blocker. Before you report `blocked` for navigation trouble, use `click-text` on the label, try the keyboard (Tab, arrows, Enter), look at `qa errors`, and read the form's source in the checkout (`git grep -n "<label>" Source/admin.web`) to learn its menu path; you have a budget for about 90 calls. `blocked` is for the environment (no session, crash, no video) and for tickets that cannot be reached in the product.

- The revision in your working directory is the one that holds the fix: when the ticket names a pull request that is not merged, the harness has checked out that pull request's head. Judge the ticket against that checkout only. Never report `not_fixed` because the change is missing from the default branch or because you could not find it: if you cannot find the ticket's change in your checkout, that is `blocked` (say what you looked for). A hand-back moves the ticket to a developer, so it needs a failure you SAW in the running application, with a screenshot of it (`qa screenshot <name>`); the tool refuses it without one. Do not run the repository's unit tests, Vitest or builds to decide a verdict: they can fail here for reasons of their own (no bun, no network, other tools) and the repository's CI already runs them. If the acceptance criteria are about something the browser cannot show (logging, build output, test coverage), the result is `blocked` with the reason "not verifiable in the browser", never `not_fixed`.

## What to report
- In the ticket comment name the **front-end revision** (the full commit SHA of your checkout) and the **back-end revision** when your brief or the application tells it, plus the video's file name, the fixtures with their keys, and the acceptance checks you ran.
- Finish with the single fenced JSON report described in your standing orders.
