11. PLANNED: EVENT HUB (triggers for the agents)
--------------------------------------------------------------------------------------
Working name: "event hub" / "trigger router". It is not just a scheduler: it ingests events from
outside and inside, decides what they mean, and tells the right agent to do something. The
domain only moves tasks and messages that something else submits; today nothing watches the world.
What it does:
- Time triggers: cron-style schedules with a time zone, jitter, and a missed-run policy (skip,
  run once, run all). Example: nightly review of open pull requests, a daily health check.
- External events in: webhooks from code hosting (pull request opened/updated/merged, push, check
  failed), the issue tracker (ticket moved to a status, label added, comment), chat (Slack/Telegram
  events), monitoring (alert fired/resolved from the log/metrics stack), the hypervisor and
  anything with a webhook. Plus polling adapters for sources that cannot call out.
- Internal events in: SomeWork task events (finished, failed, waiting for input), agent liveness
  changes, approvals pending too long, budget limits reached, new commits on a watched branch.
- Output: submit a task to a capability (with a budget), send a message to an agent or to the
  manager, start a chain (developer -> reviewer -> QA), or just notify the owner. Every output is an
  ordinary SomeWork task/message under the hub's own identity, so policy, approvals, budgets and
  the audit trail apply unchanged.
Design points to settle:
- Where it lives: a new role/service (own package on the agent kit, own identity, own card or none)
  versus a feature of the domain. Prefer a separate service so the domain stays small.
- Ingestion edge: a small HTTP receiver. Nothing on the private network should be exposed publicly:
  decide between a tunnel/reverse proxy with an allow-listed path, a relay that the hub polls, or a
  provider-side queue. Each source gets its own secret/signature verification (HMAC or signed
  headers), replay protection (timestamp window + delivery id), size limits and rate limits.
- Event model: normalise everything to one envelope (id, source, type, subject, time, data, trace)
  such as CloudEvents; keep the raw payload only briefly and never log bodies that may contain
  code, customer data or secrets. Redact before storage.
- Durability: persist accepted events before acknowledging them (the domain outbox pattern or a
  JetStream stream); at-least-once delivery with a stable idempotency key per event so a retried
  webhook never creates a second task. Dead-letter queue and a way to replay.
- Rules: declarative, versioned, reviewable (files in a repository, not clicked together). A rule
  = match (source, type, filters on fields, schedule) + action (capability, input template, budget,
  target agent) + guards (rate limit per rule and per subject, dedupe window, quiet hours,
  daily budget, require owner approval before the first run).
- Loop protection: events caused by the agents themselves (a pull request the developer agent
  opened, a ticket comment the QA agent wrote) must not trigger the same agents again. Tag
  outputs, ignore own events, cap chain depth.
- Safety: the hub's identity may invoke only an explicit allow-list of capabilities; write
  capabilities stay behind the manager's approval path; untrusted event text is data, never
  instructions (it is passed to agents as quoted context, with the source marked untrusted).
- Operations: health endpoint, metrics, structured logs, a section in the fleet dashboard (events
  in, rules fired, dropped/deduped, dead letters, oldest pending), and a kill switch per rule and
  per source.
- Testing: a fake webhook sender with recorded real payloads, signature failure cases, replay and
  duplicate deliveries, clock skew, a rule that would loop, and a real end-to-end chain on the pilot.
- First useful rules to ship: pull request opened -> reviewer task; ticket enters the testing
  status -> QA task (approval-gated writes); alert fired -> message to the manager; nightly
  schedule -> status digest to the owner.
