C. HOW MUCH DOES ONE AGENT COST, AND SHOULD AGENTS START ON DEMAND?
- Measured 2026-10-06 (idle, a few minutes after real work): a Linux agent is three small containers: agent about 65-85 MiB, sandbox 35-70
  MiB, egress proxy 25-30 MiB (limits 1 GiB, 2-3 GiB, 128 MiB), CPU about 0-1 percent; so roughly 150-190 MiB each, a few percent of one
  core while idle. Hub 66 MiB, receiver 42 MiB, domain 63 MiB, broker 32 MiB, Woodpecker server 30 MiB, CI runner 25 MiB. The Linux side is
  cheap enough that on-demand start brings almost nothing.
- The expensive part is the VMs: each Windows clone is configured with 8 GB and uses about 7.3-7.5 GB (Windows, SQL Server about 0.5 GB,
  Edge, the agent), the original Windows build station 16 GB, the dev station 32 GB (9.9 GB used), the agents VM 16 GB (about 2 GB of
  processes, the rest cache), services 4 GB, DMZ 8 GB, observability 6 GB, CI runner 4 GB. The configured memory of all VMs adds up to
  about 102 GB on a host with about 94 GB, so it relies on ballooning and cache; nothing is idle-proof.
- Idea: start Windows machines on demand. A small "wake on work" supervisor (in the hub or on the agents VM) watches the work queue for
  `code.windows` and `qa.verify` (the work-ready notifications already exist) and, through the scoped Proxmox token (power management on the
  `somework` pool only), starts the VM, waits for the agent's heartbeat, and shuts the VM down through the guest agent after N idle
  minutes. Tasks simply queue meanwhile (the catalog already shows "queueable"). Cost: a cold start of several minutes (Windows boot plus
  SQL Server start about 3 minutes; the QA app server does not start at boot by design, it would have to), and a policy for jobs that
  must start now. Benefit: 16 GB of host memory while idle, plus fewer processes to patch.
- Also consider: stopping the original Windows station and the dev station when unused, a cap per agent for concurrent sandboxes, and
  whether the three Linux agents should share one sandbox/egress pair (saves about 100 MiB each, loses isolation, probably not worth it).
- Decision needed: [DECISION] acceptable cold-start latency for Windows work, and which machines may be powered off automatically.

E. TRIED upm (https://github.com/unjs/upm) FOR THE CI INSTALL, ABANDONED 2026-10-06 (the pipelines were switched in a working copy, benchmarked and reverted; nothing was committed)
- Benchmark on the CI runner VM (2 vCPU, node 22.19.0, npm 10.9.3, one fresh container per run, medians of 3): install only: npm ci
  --ignore-scripts cold 28.5 s, warm cache 23.5 s; upm install --frozen-lockfile cold 20.5 s, warm store 12.1 s; installing the tool itself
  (`npm i -g upm`) costs 5-6 s in every step that needs it. Whole check job (install + role check + 4 test steps + rule validation), two
  runs each: npm 27.5 / 26.9 s install, upm 23.2 / 22.5 s install including the tool install; the test steps take 57-60 s for the hub and
  receiver alone and are the same either way (same test counts, all green), so the job gets about 4-5 s (4 %) shorter. A baked CI image
  with upm preinstalled would add about 5 s more; a warm store volume on the runner would bring the install down to about 12 s.
- Costs and risks: (1) upm cannot read a workspace package-lock.json ("delete it to switch to upm"), so CI uses its own `upm.lock` (47 KB,
  generate with `rm package-lock.json; upm lock` in a scratch copy, commit it, and regenerate whenever dependencies change; CI fails on a
  stale lock). Two lockfiles can drift, and CI no longer tests the dependency set developers install; (2) upm ignores `legacy-peer-deps=true`
  from .npmrc: its lock has 159 packages against npm's 127, the extra 32 include the whole @earendil-works/pi-coding-agent and its tree
  that .npmrc says must not be installed, node_modules is 183 MB against 143 MB, and 4 packages resolve to additional versions; (3) upm is a
  prerelease (1.4.0, one maintainer, "not stable yet" in its README) and skips lifecycle scripts like our existing `--ignore-scripts`; its
  minimum release age default is 1 day, our workstation policy is longer. A node_modules installed by upm in one container works in another
  container that only shares the workspace (checked), because its virtual store lives in node_modules/.upm.
- Verdict: a small gain for real extra maintenance; the owner decided it is not worth it. Reverted to `npm ci --ignore-scripts`.

D. TELEGRAM AND SLACK AS EVENT SOURCES, AND HOW A BOT RESPONDS OR STARTS A CONVERSATION (design question, supersedes the manager-only
   plan in section 10 where they differ)
- The hub only moves things IN: a webhook becomes an event. A chat message is just another event (`telegram.message.received`,
  `slack.message.received`, `slack.app_mention`, `slack.interaction.button`). Replying or starting a conversation is the other direction
  and is not something the hub does: it needs a bot token, a destination and a policy. Proposal: a CHANNEL GATEWAY, one principal per
  channel (today the manager plays this role for Telegram), that alone holds the outbound bot credentials and offers a capability
  `chat.send` (side effect: write, because people see it). Anyone who wants to speak (a rule's reaction, a woken agent, the manager)
  submits a `chat.send` task with {channel, target, text, replyTo?, thread?}; the gateway applies the policy and posts.
- RESPONDING: the inbound event carries a reply handle `{channel, conversation, thread/message id}` (never the bot token). The agent that
  handles the event answers with `chat.send` using that handle, or the rule's reaction does it. Slack: reply in the same thread;
  Telegram: reply to the message id. Long work: post "working on it", and the task result later in the same thread.
- INITIATING: events and schedules can start a conversation (alert -> owner, nightly digest, a pull request opened, a fix task needs a
  decision). Targets are an ALLOW-LIST kept in the gateway: the owner's direct message by default, named channels only when listed;
  an unknown target is refused (or asks the owner to approve it once). Per-target rate limits, quiet hours, redaction of tokens and long
  strings (as the manager already does), and a size cap; no raw task content, source code or secrets; text from events is quoted data.
- APPROVALS AS BUTTONS: write-class approvals (pull requests, Jira writes) become interactive messages (Telegram inline buttons exist
  already in the manager; Slack Block Kit buttons). The click arrives as an inbound `*.interaction` event; the gateway checks that the
  clicker is the paired owner and decides the approval.
- WHO MAY TALK TO WHOM: inbound is allow-listed by user id (the owner), DMs only to start; channel mentions only in listed channels. A
  message never causes anything except an event; the existing rules decide what runs. Agents never talk to Slack/Telegram directly.
- TRANSPORT PER CHANNEL:
  * Telegram: today the manager uses long polling; with a webhook (`setWebhook` to the public receiver, token in the path plus the
    `X-Telegram-Bot-Api-Secret-Token` header checked by the receiver) the manager's polling must be switched off (a bot has either one).
    Decide: keep long polling inside the gateway (simple, nothing public) and publish `telegram.*` events from the gateway itself, or move
    to the webhook path (one door, but the gateway then depends on the hub for intake).
  * Slack: either Socket Mode (the gateway opens an outbound websocket, no public URL, the plan in section 10) or the Events API through
    the receiver: needs the synchronous `url_verification` challenge answer (the receiver is asynchronous, so a tiny special case), the
    `X-Slack-Signature` HMAC with the 5-minute timestamp window as the verification mode, form-encoded interaction payloads, and the 3
    second acknowledgement (the receiver already answers immediately). Leaning: Socket Mode inside the gateway for Slack, webhooks only for
    sources that cannot call out.
- WORK ITEMS: define `chat.send` (card, input schema, limits, allow-list file under rules/ or deployment config), the reply handle in the
  event envelope, a gateway role (or the manager generalised) with Telegram and Slack adapters behind one interface, mapping files
  (JSONata) for the inbound message and interaction events, tests with a fake Slack and a fake Telegram, the allow-list and quiet-hours
  policy, rules for the first flows (alert -> owner, digest -> owner, approval buttons), and a decision on credentials (bot tokens only in
  the gateway host, signing secrets only in the receiver/hub).
- Decision needed: [DECISION] long polling vs webhook for Telegram, Socket Mode vs Events API for Slack, and whether the manager becomes the
  gateway or a separate principal per channel.
